# Traitfolio — full audit, 2026-07-26

Four parallel deep-dive passes over the whole repo (184 TS/TSX files, 18,623 LOC): **Upstash bandwidth**,
**dead code & doc drift**, **multi-chain readiness**, and **performance / correctness / security**.

Everything in "Applied" is already committed and `npx tsc --noEmit` is clean. `npm test` and `npm run build`
could NOT be run from the cloud session (the checked-in `node_modules` carry the win32 esbuild binary, so
`tsx` throws `TransformError` on Linux) — **please run both on your machine before pushing.**

---

## The one-paragraph version

The bandwidth blowout is understood and mostly not where it looks. The freq-table dedupe worked — details
dropped ~5×, from 19.8 KB to 3.9 KB each, measured across your own cache by fetch date. That fix just
promoted `slimlist2` (1.05 MB avg) and `vidx` (334 KB avg) to be **78% of the bill**, and those are only
fixed by R2 — which, based on your `.env` files, **is very likely not switched on**. That's finding #1 and
it's a config change, not code. Separately, the audit turned up a live valuation bug that has been silently
writing zeros for every sub-0.01-XCH collection, a build lock that disabled itself during exactly the
conditions it exists to prevent, and three unauthenticated endpoints that let anyone trigger full collection
scans. Those are fixed. The multi-chain expansion is very achievable — roughly 7–9 engineer-weeks — but
three specific things get ~3× more expensive the longer you wait, and one of them (cache keys) is a
silent-wrong-data risk rather than a cost risk.

## 1. Upstash bandwidth

### Measured cost model
Byte sizes below are **measured**, not estimated — read from your local write-through mirror
(`.cache/traitfolio-cache.db`, 636 MB, 34,439 details), which stores byte-for-byte what goes to Redis.

| Key | Contents | Avg | Max | R2-eligible? |
|---|---|---|---|---|
| `tf:kvz:slimlist2:{col}` | collection roster | **1.05 MB** | 2.67 MB | yes |
| `tf:kvz:slimscan:{col}` | roster scan checkpoint | 490 KB | **4.37 MB** | yes |
| `tf:kvz:vidx:{col}` | per-NFT value index | **334 KB** | 783 KB | yes |
| `tf:kvz:rarityfreq:{col}` | rank/freq table | 322 KB | 651 KB | yes |
| `tf:kv:comps:{col}` | comps model inputs | 54 KB | **260 KB** | **no — uncompressed** |
| `tf:kv:sales:{col}` | Dexie completed sales | 37 KB | **344 KB** | **no — uncompressed** |
| `tf:d:{id}` | NFT detail | **3.87 KB** (was 19.8 KB) | 166 KB | no |

One **cold** binder view for a 12-collection wallet ≈ **21.3 MB**, of which only ~4.6 MB is Redis-only work
that R2 wouldn't absorb. At 100 binder views/day that's **~64 GB/month today vs ~14 GB/month with R2 on** —
which lines up with the ~90 GB you burned.

### ⚠️ Finding #1 — R2 is very likely inert. Check this before anything else.
`src/lib/db/blobStore.ts:127` requires **all four** of `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`,
`R2_SECRET_ACCESS_KEY`. None appear in your `.env` or `.env.local`. If they aren't set in Vercel either,
`getActiveBlobBackend()` returns null and every large blob still reads and writes Upstash — **the entire
structural fix is doing nothing.** A wrong secret degrades *silently* to Redis.

**Verify:** `GET /api/cache-health` → `blob.backend === "r2"`, `blob.ok === true`, `blob.stats.gets`
climbing, `lastError === null`. Estimated saving if it's off: **~78% of Redis bandwidth, ~50 GB/month.**

### Applied
- **kvz byte counters were never recorded.** `redisPutLargeB64` never called `_notePut`, and sharded reads
  counted only the manifest — so a 2.67 MB roster was booked as ~60 bytes. You were about to verify finding
  #1 with instruments that report your biggest keys as free. Fixed both sides. *(`nftCache.ts`)*
- **Unpriced events were 38% of every detail blob** and are never read — every consumer filters to priced
  sale events and caps at 20. Now filtered at store time. ~1.2 MB per binder view, ~30% of all remaining
  detail bandwidth, and this is Redis traffic **R2 never touches**. *(`mintgarden/client.ts`)*
- **A 40-collection whale pulled 40 rosters + 40 value indexes in one page load (~55 MB).** The `budgetMs`
  deadline check sits inside a `Promise.all`, so every collection evaluates it at t=0 and all 40 pass —
  the budget bounded nothing. Capped to 10; the overflow already flows through the `coldCols` path the
  client enriches progressively. *(`portfolio/artifactStamp.ts`)*
- **Holdings memo raised 45s → 5min.** The Redis read it fronts already serves data up to 30 min old, so
  this changes worst-case staleness from 30m45s to 35m while cutting whole-roster re-reads ~6.7×. The
  user-facing Refresh button passes `fresh:true` and bypasses it entirely. *(`mintgarden/owner.ts`)*
- **The recent-sales rail ran a blocking 30-page Dexie scan it was explicitly designed to skip.**
  `cacheOnly` was built for it ("adds zero upstream load") and never passed — `grep` found the flag used
  only inside its own definition. On a cold collection this ran *after* the roster scan had already spent
  35s of a 60s budget: that is your cold-collection 504. *(`collections/liveCollection.ts`)*

### Open — needs your call
- **Move `comps:` and `sales:` to the large-blob seam.** Both are written with plain `cachePut`, so they're
  uncompressed and can never move to R2 — 54 KB and 37 KB average, 260 KB and 344 KB worst case, read per
  collection per cold lambda. It's a one-line swap each (`cachePut` → `cachePutLargeAsync`) and the key just
  re-warms on first miss, but it changes a persistence format so I left it for you. ~85% and ~90% cuts.
- **`vidx` as a Redis hash.** `/api/values` pulls the entire 334 KB index to look up as few as 1–5 ids.
  `HMGET` of just the held ids turns that into ~200 bytes. Free once R2 is on, so only worth it if you want
  it cheap on Redis too.
- **The daily rewards cron.** It's live in `vercel.json` and gated on `REWARDS_SHADOW`, which is `=1` in
  your `.env.local`. If it's also set in Vercel it costs ~5–8 MB/run ≈ 0.15–0.25 GB/month. Honest answer:
  **that's 0.3% of the bill — this is not your problem.** Disable it for tidiness if you like, but don't
  expect a dent. Given the token is on hold, unsetting `REWARDS_SHADOW` in Vercel is zero-risk.

## 2. Correctness & security

### 🔴 Applied — CRITICAL: the build lock failed OPEN during exactly the conditions it guards against
`nftCache.ts` `tryLock()` returned `true` on a Redis error. So the moment Upstash got slow or hit its
command quota, **every** concurrent instance believed it held the lock and started the same full collection
scan — while `cacheGet` was also failing, so every request was a cold scan. MintGarden 429s, the per-instance
cooldown is 1.5s, and the site enters a scan/429 spiral it can't exit until traffic stops. This is the
429-storm amplifier the lock's own comment says it exists to prevent. Now fails **closed** on error (callers
already handle lock-loss by serving the warming state); Redis simply *not configured* still returns true, so
local dev is unaffected.

### 🔴 Applied — HIGH: every sub-0.01-XCH collection was being valued at zero
`valuation/estimate.ts` rounded XCH to **2 decimals**. A collection with a 0.004 XCH floor — common on
Chia — passed the `> 0` guard and then `round(0.004) = 0`, so every premium multiplied to 0 and the API
returned `totalEstimate: 0` for a grail whose baseline is 0.056 XCH. Worse, that 0 was persisted into
`vidx:` for 24 hours and stamped over the collector's binder cards. Non-zero floors were distorted too:
0.014 → 0.01 is **−29%**. Now 6dp for XCH, 2dp for USD only. Verified by compiling and running the real
function:

```
before:  floor 0.004, rank 1/10000  ->  total 0        (grail shows "0 XCH")
after:   floor 0.004, rank 1/10000  ->  total 0.06     (floor 0.004 + rarity 0.056)
         floor 1.2,   rank 12/10000 ->  total 17.048425  (unchanged in substance, more precise)
```

### 🔴 Applied — HIGH: three unauthenticated routes let anyone burn a 60s function
- **`/api/binder`** validated ids only as `typeof === "string"`. 120 arbitrary strings all miss the cache and
  each runs a 3-attempt × 6s retry loop = **~208 seconds of work dispatched by one 3 KB POST**, killed at
  `maxDuration` having achieved nothing, after 360 upstream requests on the *unpaced interactive* lane.
- **`/api/values`** filtered on `startsWith("col1")` only, and each miss kicked a full background collection
  scan via `keepAlive` — plus `_lastKick` grew 60 entries per request and never evicted (an OOM path).
- **`/api/nft-debug`** had no gate at all and ran `getAllCollectionCards()` on a caller-supplied id with
  `maxDuration = 60` — an unauthenticated full-collection scan trigger, which is precisely what `/api/warm`
  is `CRON_SECRET`-gated to prevent.

Added `src/lib/chia/ids.ts` (`isCollectionId` / `isNftId` / `isSaneAmount`) and applied it at every public
entry point; bounded `_lastKick`; gated `/api/nft-debug` to non-production like `/comps-status` already is.

### 🔴 Applied — HIGH: `/_next/image` was a public open image proxy, for no benefit
`next.config.mjs` allowed `hostname: "**"`, so `/_next/image?url=https://anything` made Vercel fetch an
arbitrary URL server-side — a proxy/reflection primitive using your IP and egress, billed per transformation
and trivially cache-busted via `w`/`q`. Meanwhile **every** external NFT `<Image>` in the app already passes
`unoptimized`, so the optimizer was doing nothing for you. Set `images.unoptimized: true` and narrowed
`remotePatterns` to MintGarden. If you ever want the optimizer back, narrow the host list first.

### 🟠 Applied — MEDIUM
- **Dexie calls had no body timeout.** `clearTimeout` sat in a `finally`, which fires when response *headers*
  arrive — so an upstream that sent `200 OK` then stalled the body hung with no ceiling until the whole
  function was killed. All 9 Dexie call sites were exposed. MintGarden's client gets this right; Dexie's
  didn't. *(`market/dexie.ts`)*
- **The rarity scan held a 90s lock it never released, with no deadline.** `releaseLock` was never even
  imported. On a large unranked collection the scan outlived the 60s function, nothing was checkpointed,
  and the lock stayed held for its full TTL — so every retry in that window returned null and the next
  attempt restarted from page 1, burning ~600 MintGarden requests each time and **never converging**. Added
  a 35s budget (partial tally beats a killed function) and a `finally` release. *(`rarity/collectionFrequency.ts`)*
- **`generateMetadata` fetched MintGarden for any junk path segment**, ahead of the page's own guard — every
  hit to `/collection/<anything>` was a dynamic SSR + an upstream call + a permanent in-process cache entry.
- **The retry loop slept its backoff after the final failed attempt** — 1.6s of pure function time wasted per
  permanently-dead id, which is what made the `/api/binder` amplification above so effective.

### 🟠 Open — needs your call
- **`REWARDS_OPS_SECRET` travels in the URL and is serialized into the browser.** `/collection/[id]?ops=<secret>`
  passes it to `RewardsDashboard`, a **client** component — so the secret lands in the RSC flight payload
  embedded in the HTML, plus Vercel access logs, browser history, and any proxy log. Anyone holding it can
  download the full per-wallet settlement manifest or flip an epoch to `paid` (monotonic, non-reversible).
  Mitigated by being behind `REWARDS_SHADOW`, and the compare itself is correctly constant-time — the flaw
  is the *transport*. Since rewards are on hold, the cheapest action is unsetting `REWARDS_SHADOW` in Vercel;
  the real fix (header/cookie auth) can wait for the relaunch.
- **`/api/status`, `/api/cache-health`, `/api/seed-health` are unauthenticated.** `?deep=1` on `/api/status`
  runs up to 60 Redis SCAN commands *per request* — a few hundred requests exhausts your Upstash command
  budget, which then triggers the lock storm above. `/api/cache-health` performs a real Redis write **and**
  an R2 put/get on every call. They also leak your Redis hostname, key counts, and p50/p95/p99 latencies.
  Fix is ~5 lines each using the `opsSecretMatches` pattern you already have — I left it because these are
  genuinely useful operationally and you may want them reachable without a secret.
- **`/api/collection/[id]/all` ships 13.46 MB of JSON per collection open** (measured on real Misfitz data:
  1,396 bytes/card × 10,000; 1.07 MB gzipped). The browser parses and retains all of it — a ~200–400ms
  main-thread block plus sustained mobile heap — to render 48 visible cards. You already solved exactly this
  for `/api/holdings` with `ROSTER_CHUNK`. A slim grid projection (~200 B/card) plus lazy traits on modal
  open would cut it ~85%. Medium effort, real mobile win.
- **Warmset poisoning.** `valueIndex.ts` merges new collection ids **first** then caps at 300, and the input
  is unauthenticated wallet content. Someone holding NFTs across 300 junk collections can evict every real
  collection from the warm set for 30 days, and `/api/warm` then spends its whole budget on them. Fix is
  frequency-weighting (≥2 distinct wallets) rather than recency-first.
- **`/api/warm` is documented as cron-driven but is NOT in `vercel.json`.** So the nightly warmer that
  pre-builds rarity tables and comps — the thing that stops first visitors eating a cold 30–70s scan —
  **never fires in production.** I did not add it: turning it on will *increase* Upstash bandwidth, and that
  tradeoff is yours to make while the limit is still reset-pending. Worth doing right after R2 is confirmed.
- **Twelve unbounded module-level `Map`s** (`liveCollection._fullCache` holds multi-MB per collection). A warm
  lambda serving 60 collections can accumulate ~780 MB and OOM. The bounded-LRU pattern already exists in
  `_detailJsonMemo` and `_holdMemo` — it just wasn't applied to the other twelve. I fixed the one that was
  attacker-controlled (`_lastKick`); the rest is a mechanical sweep.

### Verified clean — don't re-audit these
No SSRF from user ids (real bech32m checksum, everything else `encodeURIComponent`'d — the image optimizer
was the *only* arbitrary-URL server fetch). No XSS (two `dangerouslySetInnerHTML`, both static/escaped; all
NFT metadata renders as React text children). No open redirects. Operator auth SHA-256s both sides then
`timingSafeEqual`s. The comps math is numerically sound — non-finite filtering, clamped percentiles,
winsorized prices. `BinderView` does not have a 1000-card render problem (it renders ≤48 regardless).

## 4. Multi-chain readiness (Robinhood Chain)

**Verdict: wide but shallow coupling — much better than the file count suggests.** ~110 of 180 files mention
Chia/XCH/MintGarden/Dexie, which looks catastrophic and isn't. `comps.ts` (374 lines) has **zero** currency
assumptions — it fits a curve to `{rank, price}` and has never heard of XCH. Five of seven rarity files are
already chain-free. `NftData` is already the neutral domain type every component consumes. What you actually
have is **vocabulary coupling** plus one load-bearing implicit predicate.

### The three things that get ~3× more expensive if you wait
1. **Cache keys have no chain dimension.** This is the only *silent-wrong-data* risk in the whole audit.
   `holdings3:0xabc…` is the same key on every EVM chain — an EOA has the same address everywhere. The
   moment Robinhood Chain is joined by a second EVM chain, or someone points the adapter at Arbitrum for
   testing, one key holds two chains' rosters. Every cache layer is `catch`-guarded to degrade silently, so
   **there is no error path — it just serves the wrong NFTs.** Fix now (`tf:{type}:{chain}:{id}`, enforced
   in the type system so a chainless key is a compile error): under a day, no migration needed since it's a
   pure TTL'd cache. Fix after mixed-chain keys reach production: an incident you can't detect from logs.
2. **`startsWith("col1")` — 33 occurrences across 11 files**, silently doing the job of "is this a real
   on-chain collection." Needs splitting into `isLiveRef()` and `chainOf()`. Linear tax on every week you wait.
3. **The URL scheme.** `/collection/[chain]/[id]` with a 301 resolver on the old form. **Your SEO exposure
   is currently near-zero** — `sitemap.ts` lists only 3 static URLs and collection pages were never
   submitted. That window closes permanently the moment you do a marketing push.

### The genuinely hard problems (each needs a real decision, not hand-waving)
- **Identity.** Chia: one globally-unique `nft1…` launcher id. EVM: `(contract, tokenId)`, and the same
  contract address exists on multiple chains, often deliberately. Recommendation: branded chain-qualified
  strings (`"chia:col1…"`, `"rhc:0xabc…/1234"`) — **not** objects, because these must work as Map keys,
  cache keys, URL segments, and React keys, which is exactly how ids are used today.
- **DIDs have no EVM equivalent.** Don't invent one. Model owner input as a discriminated union; the correct
  EVM answer to "show everything I own" is "paste more addresses" — which your UI already asks for.
- **The sales feed is the hardest new build.** Dexie gives you a clean curated completed-offers feed. EVM has
  no equivalent: raw `Transfer` events are *not* sales (mints, airdrops, consolidation, burns all look
  identical and carry no price). Real prices live in marketplace fill events, per-marketplace schemas, with
  a varying payment token. **Before committing to this phase, spike what indexer and marketplace actually
  exist on Robinhood Chain** — if there's no sales API, RHC ships floor-only and the comps model stays
  Chia-only. That single unknown is the difference between a 2-week and a 4-week phase.
- **The binder's headline number.** `myHoldings` sums `totalEstimateXch` — under multi-chain that's adding
  XCH to ETH. Cross-chain aggregates have to become **USD**, with a per-chain native breakdown beneath. That
  makes USD load-bearing when it is currently explicitly cosmetic and seeded from a hardcoded fallback.
  **This is a product decision and it's yours** — the binder's headline changes denomination.
- **ERC-1155 breaks the singleton model** (many owners per tokenId, so rank uniqueness and "you own this"
  stop meaning anything). Scope to ERC-721, detect 1155 via ERC-165, and skip with a clear message.

### Phased plan — ~7–9.5 engineer-weeks
| Phase | Work | Est. | Ships |
|---|---|---|---|
| 0 | Ref types, chain-namespaced cache keys, kill the `col1` predicate | 0.5–1w | Identical Chia app; pure refactor |
| 1 | `/collection/[chain]/[id]` + redirects; currency vocabulary; `OwnerRef` union | 1–1.5w | Identical app, multi-chain-shaped |
| 2 | Extract `ChainAdapter` from real call sites; move pacing state per-adapter | 1.5–2w | Identical app, one adapter registered |
| 3 | Robinhood Chain adapter | 3–4w ⚠️ | RHC browsable + valued, flag-gated |
| 4 | Cross-chain binder, chain filters, copy sweep | 1–2w | The stated vision |

Every phase before 3 is a refactor with **zero user-visible change** — Chia keeps working throughout.

### Do NOT do these
- **Don't revive the deleted `DataSource` interface** (`git show 2dda90a^:src/lib/data-sources/types.ts`).
  Its 4-method shape can't express cursor paging, background pacing, batched detail reads, per-call timeouts,
  checkpoint/resume, or partial results — all of which is hard-won performance work in `client.ts` and
  `owner.ts`. Define the interface from the call sites, not from a whiteboard. It was deleted for a reason.
- **Don't abstract rarity or the valuation math.** Both are already chain-free. Rename fields; touch nothing.
- **Don't introduce BigInt or a decimal library.** Parse wei at the adapter edge, hand the model a float.
  Float64 gives ~15 significant digits for a 2-decimal *estimate*.
- **Don't port `src/lib/rewards/` or `src/lib/tang/`.** Both are intrinsically Chia-specific. Fence behind
  `chain === "chia"`.
- **Don't build a config-driven chain registry.** With two chains a TypeScript `Record<ChainId, ChainAdapter>`
  is better: exhaustiveness-checked, no runtime resolution. The deleted plugin registry is the cautionary tale.
